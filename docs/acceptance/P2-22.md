- 结果：2 个 Playwright 场景全部通过

## 场景① ERP 订单到发运事件回写

通过 HTTP 完成 ERP 销售订单创建、同键同内容重放、同键异内容 409、提交、自动审核、ATP 分配、履约释放、WMS 出库单释放、波次计划与分配、RF 拣选与复核、包装测量与封箱、标签、集货、装车和并发发运。

验收断言：

- 订单状态按 Draft→Open→Approved→Allocated→Released 推进，生成履约单和运输需求引用。
- 波次分配后生成拣选任务，RF 相同设备序列重放只保留一条 PickConfirmation。
- RF 离线队列相同命令重放返回原 commandId，只保留一条 OfflineCommand。
- 两个并发发运请求返回同一 dispatchId，仅一方为首次处理。
- 库存最终 onHand/available/allocated 均为 0，仅产生一条 SHIPMENT 流水和一条 `outbound.shipped.v1` Outbox 事件。

## 场景③ 并发分配与重放

两名独立账号分别登录并提交各需 4 EA 的订单，同时竞争仅 5 EA 的 ATP 投影。

验收断言：

- 两个分配结果严格为一个 ALLOCATED、一个 FAILED。
- 投影 allocated 为 4 EA，不超出 5 EA 可用量。
- 两名用户的请求都经过后端 RBAC 决策；第二账号留下独立 `oms.order.allocate` 允许审计。
- 场景①中的 RF、离线队列和发运重放共同证明重复请求不会重复扣减库存。

## 验收修复

Playwright 首次穿过真实 HTTP 响应时发现 WMS 工作台直接返回 Prisma BigInt，导致 JSON 序列化 500。新增统一 HTTP JSON 转换，将设备序列稳定输出为字符串，并应用于拣选、包装发运和移动作业工作台。

Playwright 与 Vitest 已分目录执行：常规测试仍由 `pnpm verify` 运行，验收测试由 `pnpm test:e2e` 运行，不跳过任何套件。
