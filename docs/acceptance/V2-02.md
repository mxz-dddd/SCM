# V2-02 持久化事件投递验收

## 结果

- Outbox 发布与消费者处理状态已分离：发布事务先按静态订阅幂等写入全部 `EventDelivery`，然后才把源 Outbox 标记为 `PUBLISHED`。
- Delivery claim 使用 PostgreSQL `FOR UPDATE SKIP LOCKED`，并按 `tenant + consumer + partitionKey + sourceOccurredAt + sourceEventCreatedAt + eventId` 阻塞后序事件。
- 每个消费者独立维护租约、尝试次数、退避、响应快照、失败与死信；必需消费者的死信持续阻塞同分区，直到显式重放或人工跳过。
- Worker 不再向 BullMQ `scm-events` 写入后立即确认 Outbox，也不再调用通用空 handler；它只调用静态 allowlist 中与持久化订阅完全一致的领域端点。
- Event Workbench 同时展示 Outbox、Delivery、Inbox、Checkpoint，并支持 Outbox 与消费者死信的独立重放。

## 自动化证据

- 同分区 v3 先插入、v2 后插入，两个并发 claim 只返回源顺序更早的 v2。
- 前序 `PROCESSING` 或未到期 `FAILED` 时后序不可领取；前序完成后后序释放。
- 不同 partition 可在同轮并行领取。
- 同一 event/consumer 的 fan-out 幂等重放不新增 Delivery。
- 同一事件的两个订阅可分别进入 `PROCESSED` 与 `FAILED`。
- 仅死信订阅被重放，已成功订阅保持终态且不重复领取。
- `EVERY_EVENT` 同 aggregateVersion 的不同 eventId 均执行 handler。
